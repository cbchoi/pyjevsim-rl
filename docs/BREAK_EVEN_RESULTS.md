# 손익분기 연구 부분 실행 결과

2026년10월5일, 코호트 `results/break-even-20261005-01`.

**현재 결론:** 큰 계산량에서 공통 복원 C1이 매번 재실행하는 R보다 빨라지는 사례를
관측했다. 그러나 calibration6개 family 중1개만 수행했으므로 손익분기 예측을
확증한 연구가 아니다. 모델 전용 복원 N보다 빠르다는 증거도 없다.

## 수행과 중단 이유

Windows11, Python3.14.0, worker1/BLAS1, `condition=unspecified`로 실행했다.
다른 프로그램을 종료하지 않았고 전용 Linux 환경 결과를 대체하지 않는다.
실행은09:57:00부터10:04:18 KST까지 약437.43초였다.

| 항목 | 계획 | 관측 |
|---|---:|---:|
| Calibration 전체 arm | 864 | 144 성공, 0 실패, 720 미실행 |
| Companion | 432 | 72 성공 |
| Timing | 432 | 72 성공 |
| 비교 셀 | 144 | 24 완료·정확 비교 수용 |
| 독립 입력 family | 6 | 1 완료: seed981000 |
| Validation / transfer | calibration 후 결정 / 216 arm | 둘 다 미실행 |
| 새 보관량 | 32MiB 이하 | 3,520,238bytes, 약3.36MiB |

첫 완전 family의 비용으로 사전 자원 규칙을 적용했다.

```text
첫 family process wall 합계 = 430.770175초
남은5개 family 예상 + 분석 여유 = 1.5 × 5 × 430.770175 + 120
                                 = 3,350.776313초
해당 시점 실제 경과 = 435.038855초
calibration 남은 예산 = 3,600 − 435.038855 = 3,164.961145초
```

안전계수를 포함한 남은 예상이 남은 예산을185.815초 초과하여 조기 종료했다.
**실제 시간 상한을 소진하거나 arm 오류가 발생한 것이 아니다.** 같은 관측 비용과
판정식을 적용하면 calibration 상한이 최소3,785.815초여야 이 판정을 통과한다는
산술적 의미일 뿐, 그 시간이면 완료된다는 보장이나 새 예산 승인이 아니다.
재시작·실패 arm 대체·조건 삭제·K/N 완화·이전 자료 혼합은 하지 않았다.

각 stage의 전체 수용은 false, 분석 상태는 partial이다. `s_max=null`이며 표본 수 N과
고정 예측 좌표를 선정하지 않았다. `predictions.json`은 생성되지 않았다. 생성된
calibration 요약의 predictions 관련 문장은 완료 후 형식을 설명한 일반 문구이며,
이번 부분 실행에서 실제 예측 명세가 있다는 뜻이 아니다.

C1은 K4096의6개 조건에서만 R보다 빨랐고, K1/16/256의18개 조건에서는 느렸다.
S8/K4096/B16에서 R12.6499초 대비 C1 6.7590초로 약46.6% 짧았고,
S512/K4096/B16에서는 약39.4% 짧았다. 이는 선택적으로 수집한 좋은 조건이 아니라
사전 grid 전체24개 조건을 수행한 첫 family의 기술 결과다.

N은 R보다21/24조건에서 빨랐고 C1보다24/24조건에서 빨랐다. 따라서 결론은
공통 복원이 모델 전용 복원보다 우월하다는 것이 아니다. 모든 S/B 조합에서 K256과
K4096의 관측 방향은 반대였지만, 그 사이의 연속적인 임계 K를 측정하거나
고정 예측으로 검증한 것은 아니다. K에 대한 단조성도 이 자료만으로 보장할 수 없다.

## 실제 생략한 작업과 잔여 비용

S8/K4096/B16의 **별도 companion**에서 관측한 값은 다음과 같다. 이 값을 timing
실행의 전체 trace를 직접 계수한 값으로 표현하지 않는다.

| 항목 | R | N | C1 |
|---|---:|---:|---:|
| Prefix 수행 | 16회 | 1회 | 1회 |
| 복원 | 0회 | 16회 | 16회 |
| Prefix 수요 risk 호출 | 1,024 | 64 | 64 |
| Prefix forecast-stage | 33,554,432 | 2,097,152 | 2,097,152 |
| Suffix 수요 risk 호출 | 256 | 256 | 256 |
| Suffix forecast-stage | 8,388,608 | 8,388,608 | 8,388,608 |

N/C1은 중복 prefix risk 호출960회, forecast-stage31,457,280회를 생략했다.
Capture/restore의 simulated model callback은0이었다. 관측된 risk 재계산 계수도
0이나, 이는 제품 검증이 꺼져 있다는 뜻이 아니다. 객체·구조·보상 상태 등의 제품
검증은 계속 수행되며 시간 구간에 포함된다.

첫 family의24조건 전체 companion 합계에서도 R의 prefix224회에 비해 N/C1은
각24회였다. 각 복원 방법이 prefix200회, 수요 risk 호출12,800회, 실제 forecast-stage
111,846,400회를 생략했다. suffix step은 각각3,584회로 같았다. 이를 개별 callback을
합산한 “고유 사건 수”로 바꾸어 표현하지 않는다.

같은 timing 조건의 coarse phase는 다음과 같다.

| 구간(s) | R | N | C1 |
|---|---:|---:|---:|
| Prefix | 10.1050 | 0.6231 | 1.2931 |
| Restore | 0 | 0.0247 | 0.9209 |
| Suffix | 2.5380 | 2.4514 | 4.4445 |
| 전체 workflow | 12.6499 | 3.1067 | 6.7590 |

재실행 생략으로 이익이 생겨도 C1에는 N에 비해 restore뿐 아니라 prefix/suffix
구간에도 추가 비용이 남는다. 위 구간별 계측만으로 각각을 특정 함수나 외부 부하의
인과 효과로 분리하지 않는다. 타당한 주장은 “실행 비용과 재사용 이익의 경계가 있다”는
관측이며 “snapshot을 쓰면 항상 빠르다”는 주장이 아니다.

24개 C1 timing 합계81.812초의 구간별 비중은 prefix+suffix72.95%, restore23.97%,
capture1.34%였다. 비교용 소규모 조건부터 큰 조건까지 합친 기술통계이므로 특정
응용의 평균 비중이나 보편적 병목 분포는 아니다. 실행 프로세스의 시작·import·전송
비용은 workflow 밖이지만 전체 연구 예산에 포함되어 자원 예측에는 process wall을 쓴다.

## 한계와 보고 원칙

- 독립 family가1개뿐이다. 저장된20,000 bootstrap draw는 같은 family를 반복 선택하여
  구간이 퇴화한다. 이 구간을 의미 있는95% 신뢰구간이나 정밀한 임계값 증거로 사용하지 않는다.
- 모든 실제 실행의 source identity와 provenance는 일치했다. `source_check.complete=false`와
  분석의 “incomplete or inconsistent” 문구는 계획된864회 전체 미완료 때문이며 관측된
  source drift를 뜻하지 않는다.
- S512/K16/B16 C1의 wall9.7372초와 CPU6.3125초는 그대로 보존한다. 이 차이를 특정
  다른 프로그램의 간섭량으로 단정하거나 불리한 이상치로 제거하지 않는다.
- 전체 lifetime memory, 외부 프로세스별 간섭, 관측 사이 최대 transient 사용량은 미확인이다.
- Companion 전체 상태·사건 비교와 timing 정상 scalar 출력 비교는 별개의 근거다.
  Timing 전체 trace를 비교했다고 주장하지 않는다.
- 이 모델의 forecast는 가상 시나리오이며 실물 재고 수요의 검증된 예측기가 아니다.
  입력구조 이전·현장 일반화·RL 수렴·정책 품질·federation·인간 생산성은 미검증이다.

## 증거와 다음 판단

실행 코드는 commit `40a551c`, 실행 직전 문서는 `cd3b9b5`다. 실행 source identity는
`1b347e937afd85369458d5dd829f694da0ec063df7c223de6a2f6c72389fc33c`다.
원래 설계 JSON의 `source_checkpoint=34d0023`는 설계의 감사 기준이며 실행 코드
commit을 뜻하지 않는다. 실행별 파일 SHA256은 새 코호트 protocol에 있다.

주요 파일은 `workflow.json`, `calibration/resource-feasibility.json`, `execution.json`,
`arms.jsonl`, `cells.jsonl`, `fit.json`, `environment.json`, `provenance/`다.
원자료와 기존 코호트는 수정·삭제·공개하지 않았다. 큰 trace와 snapshot은 사전 보관
규칙대로 비교/사용 후 정리했으므로 compact 결과에서 복구할 수 없다.

후속 연구는 사용자 판단 전에는 실행하지 않는다. 우선안은 전용 Linux에서 같은 설계를
새 코호트로 실행하는 것이다. 현재 Windows를 계속 사용한다면 총9,000초 내에서
calibration4,200 / validation3,000 / transfer1,800초로 재배분하는 방안을 승인받을 수 있다.
이는 제안일 뿐이며 첫 부분 결과를 이어 붙이거나 표본 수·유리한 조건을 고르는 변경이 아니다.
표본 수와 예측 정확도 목표 달성 가능성은 완전한 새 calibration 후에 다시 판단해야 한다.
