# 개발자 파일럿 과제 팩 — 명세 초안

TASK221 / MS45 L1, 2026년 10월 5일. 상위 계획은
[개발자 평가 프로토콜](../DEVELOPER_STUDY.md)과
[개선 설계 IMP011](../CONTINUATION_IMPROVEMENT_DESIGN.md)이다.

**상태: 과제·평가 명세만 준비됨.** 아래 두 모델의 실행 가능한 starter, 제출 API,
독립 oracle, 자동 채점기, 표준 유지보수 baseline, 참여 동의 절차는 아직 제공되지
않았다. 이 문서를 다운로드하는 것만으로 연구를 시작할 수 없다. 실제 참여자 자료,
완료시간, 생산성 개선 수치는 아직 없다.

## 목적과 과제 구성

4명의 시뮬레이션 비경험·agentic AI 경험 학생이 새 모델을 복원·개입 인터페이스에
통합하고 상태 요구사항을 변경하는 소규모 절차 파일럿이다. 기존 Q/M은 교육에만
사용한다. 기존 inventory 구현을 이름만 바꾼 답안으로 배포하거나 이미 노출된 과제를
held-out이라고 부르지 않는다.

- [TASK_A](TASK_A.md): 두 수조의 지연 주입 밸브와 공동 사용량 원장.
- [TASK_B](TASK_B.md): 두 축열기의 지연 가열 펄스와 공동 전력 원장.
- [RUBRIC](RUBRIC.md): 양 처리에 공통인 정확성·측정·실패 처리 기준.

A/B는 두 정적 구성요소, 지연 완료, 동시 사건, 공동 mutable 원장, 미래 난수 상태,
증분 보상을 맞춘 **새로운 교육용 대응 변형의 제안**이다. 상태 수가 같다는 이유로
난이도가 같다고 입증된 것은 아니다. 독립 작성·사전 dry run으로 난이도를 검토해야
한다. 구조적으로 대응하므로 두 과제를 서로 독립적인 응용 분야 일반화 증거로 세지
않는다. 미리 이 명세를 읽었거나 해결한 참여자는 그 노출을 기록하고 새 변형을 배정한다.

## 처리와 공정성

| 처리 | 허용 구현 | 동일하게 요구하는 사항 |
|---|---|---|
| N-dev-v1 | native snapshot API와 명시적 sidecar/rebind 코드 | cut·시각·상태·난수·보상·별칭·예정 사건의 정상 복원, 분기 격리 |
| C1-dev-v1 | 고정 버전 C1 strict-v1과 명시적 adapter, 값 필드 helper | 위와 같은 결과와 정상 사용 계약 |

N-dev-v1은 개발자 과제용 방법 이름이다. 기존 성능평가의 fast N과 코드·보장·속도가
동일하다고 가정하지 않는다. 양쪽 모두 제공된 동일 모델·정상 action API를 사용하며,
분기마다 source를 편집하거나 cut까지 prefix를 재실행하는 구현은 복원 답안으로 인정하지
않는다. 모델의 정상 callback 코드는 통합 단계에서 변경 금지, adapter/sidecar 변경은
허용한다. 유지보수 단계에서는 지정된 모델·보상 변경만 허용한다.

C1의 추가 source hash·일반 손상 거부·수명 검사 기능은 별도 보장 목록으로 기록한다.
이를 N의 공통 필수 점수로 사후 추가하지 않는다. 적대적 artifact, 실행 중 monkeypatch,
임의 파일 변조 방어와 성능 비교는 이 과제의 필수 요구가 아니다. 기본 snapshot format
오류가 native API에서 거부되더라도 이를 양 처리의 동등한 보안 보장으로 확대하지 않는다.

## 배정과 시간

동의한 참여자를 익명 슬롯에 무작위 배정한 뒤 순서를 기록한다.

| 슬롯 | 1차 기간 | 2차 기간 |
|---|---|---|
| P01 | C1 / A | N / B |
| P02 | N / A | C1 / B |
| P03 | C1 / B | N / A |
| P04 | N / B | C1 / A |

동일한 30분 교육과 별도 Q/M 연습 15분 후 기간별 통합 40분, 유지보수 20분을 제공한다.
과제 문서와 starter를 처음 공개할 때 통합 시계를 시작한다. 문서 읽기, AI 대기, 도구 실행,
디버깅, 제출을 elapsed에 포함한다. 통합을 일찍 끝내도 유지보수 요구는 40분 경계 전에
공개하지 않는다. 남은 시간의 대기와 통합 재검토는 구분 기록한다.

40분까지 통합 미완료 시 실패를 유지하고 동일 처리의 사전 검증된 표준 baseline을
제공한 뒤 유지보수 시계를 시작한다. baseline 제공 전 준비 시간은 별도 기록한다.
완료자는 자신의 제출을 유지보수한다. 두 시작 유형은 별도 보고하며 동일한 난이도라고
가정하지 않는다. 20분 미완료는 검열된 시간과 실패로 기록하고 성공시간으로 바꾸지 않는다.

## AI·지원·기록 통제

모델/버전, agent 도구, IDE, 인터넷 접근, reference, 비용/토큰 상한, 하드웨어를 양 처리에
동일하게 제공한다. 각 기간에는 빈 AI context와 별도 workspace를 사용하고 앞 기간 답안,
다른 참여자의 코드, 숨긴 evaluator와 reference solution을 전달하지 않는다. 참가자에게
도구 사용법과 과제별 API 참고 자료를 동일 분량·접근성으로 제공하고 실제 이용량도 기록한다.
재현 가능한 고정 모델 버전을 제공할 수 없으면 실제 버전·시각을 기록하고 한계로 보고한다.

진행자 도움은 사전 FAQ 또는 동일한 단계별 hint 목록으로 제한하며 시간·내용을 기록한다.
기반 시설 장애는 임의로 해당 참여자만 재시작하지 않는다. 계획된 외부 장애 판정자가
시계 pause와 영향 기간을 기록한다. 전체 elapsed와 장애 제외 elapsed를 둘 다 남긴다.
유리한 분석을 위해 AI 지연이나 디버깅 시간을 사후 삭제하지 않는다.

동의·기관 요구 윤리 절차·보관기간을 확정하기 전 사람 세션을 시작하지 않는다.
동의한 범위의 익명 코드·제출·AI/도구 이벤트만 수집한다. 개인 식별 자료, 녹화, raw AI
로그를 Git에 넣거나 공개하지 않는다. 외부 AI 전송과 철회 시 자료 처리도 사전 고지한다.

## 실행 전에 남은 준비 — 완료된 것으로 보고하지 않을 것

1. 새로운 A/B 원본 모델을 구현하고, 정상 동작이 동일 oracle와 맞는지 독립 검토한다.
2. 처리별 최소 starter와 동일한 제출 계약을 구현한다. 예: `create/capture/restore/step/close`;
   현재 이 함수 이름은 배포 API가 아니라 준비할 인터페이스의 설명이다.
3. rubric의 공개 예제·비공개 입력·독립 oracle·변조/격리 observer를 구현한다.
4. 표준 N-dev/C1-dev 정답과 유지보수 시작 baseline을 작성하고 문제 자료와 분리한다.
5. 코드 변경 허용 경로와 제출 포맷, 고정 API 문서, dependency/runtime 버전을 확정한다.
6. 참여하지 않는 개발자로 instruction ambiguity와 40/20분 가능성을 검토한다.
   결과에 따라 바꾸면 과제 버전을 올리고 실제 참여 전에 배정/평가기준을 확정한다.
7. 동의·익명화·AI 정책·장애 규칙·수동 또는 자동 시각 기록 도구를 준비한다.
8. 수행 직전 exposure 확인과 배정을 기록한다. 이 준비 절차는 모델 성능실험의
   smoke/freeze gate가 아니라 아직 존재하지 않는 사람 연구 도구의 제작 목록이다.

파일럿은 개별 4명 결과와 실패·순서 효과를 드러내는 데 목적이 있다. 8개 기간을
독립 참여자 8명으로 세거나 의미 있는 모집단 생산성 우위를 주장하지 않는다.
